# CyberSathi — Investigation Workbench

Enhanced hackathon prototype for financial transaction network investigation. Includes PostgreSQL support, JWT login and roles, audit logging, temporal graph patterns, complaint-to-transaction candidate matching, an Isolation Forest anomaly endpoint, PDF/JSON reports, source-record hashes, Docker Compose, synthetic data, and automated tests.

## Quick start (local SQLite)

Python 3.11+ recommended.

### Windows

```powershell
py -m venv .venv
.venv\Scripts\Activate.ps1
pip install -r requirements.txt
uvicorn app.main:app --reload
```

If activation is blocked:

```powershell
.venv\Scripts\python.exe -m pip install -r requirements.txt
.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

### macOS/Linux

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Open `http://127.0.0.1:8000`. API docs: `http://127.0.0.1:8000/docs`.

## PostgreSQL with Docker Compose

1. Install Docker Desktop.
2. Review the local-only credentials in `docker-compose.yml`; change them before use outside your machine.
3. Run:

```bash
docker compose up --build
```

4. Open `http://127.0.0.1:8000`.

Without Docker, the app defaults to local SQLite. Set `DATABASE_URL` to a PostgreSQL SQLAlchemy URL to use PostgreSQL. The tables are created on startup for this prototype; add Alembic migrations before evolving a deployed schema.

## Main features

- Transaction graph with time-window filtering
- Bounded account money-flow path exploration and transaction IDs
- Temporal pattern candidates: rapid pass-through and fan-in/fan-out
- Complaint-to-transaction candidate matching using exact account references and TF-IDF text similarity
- Transparent rule-based review-priority score with evidence transaction IDs
- Isolation Forest account-level relative anomaly scores
- Counterfactual graph structure simulation
- CSV import with basic validation, 10 MB cap, duplicate ID checks and SHA-256 source-record hashes
- JWT sign-in; roles `admin`, `investigator`, `reviewer`
- Admin can create users; admin/reviewer can inspect audit log
- PDF and JSON report export
- PostgreSQL-ready SQLAlchemy persistence
- Docker and automated API tests

These results only test the pipeline on data generated by the script; they are **not** evidence of real-world financial-fraud accuracy. Never present them as real-world validation.

## Important limitations and safety

- The bundled data is synthetic.
- Review-priority scores are rules, not calibrated fraud probabilities.
- Isolation Forest results are unsupervised relative anomalies; they are not fraud probabilities.
- TF-IDF similarity creates candidate links; it does not establish that a complaint refers to a transfer.
- SHA-256 hashes help detect later content changes when the expected hash is protected; they do not prove that a source record was authentic at creation.
- Audit logging is an initial implementation, not tamper-proof audit storage.
- JWT secret and demo credentials must be changed before deployment.
- This is not ready for sensitive operational banking data. Before real use add secure secrets management, HTTPS, rate limiting, account lockout, stronger session/token lifecycle controls, database migrations, backups, field-level privacy rules, independent security testing, robust logging retention, and model governance.

### Database migration workflow

Install dependencies, set `DATABASE_URL`, then run:

```bash
alembic upgrade head
```

To generate a future migration after editing SQLAlchemy models:

```bash
alembic revision --autogenerate -m "describe schema change"
```

Review generated migration code and SQL before applying it. Back up first. Test migration and rollback on staging. The startup setting `AUTO_CREATE_SCHEMA=false` should be used in production so schema changes are handled by migrations.

### Production mode

Set `ENVIRONMENT=production`, `AUTO_CREATE_SCHEMA=false`, a PostgreSQL `DATABASE_URL`, a strong secret from a secret manager, and a unique admin password. The app will fail startup if these core settings are not safe. This is not a substitute for a security review, HTTPS, rate limiting, robust session lifecycle, monitoring, and penetration testing.
